# Lab 04: Perimeter Defense, Egress Filtering & Network Threat Hunting (pfSense + Splunk)

## Why I Built This Lab

Adversaries must traverse the perimeter to conduct external reconnaissance, establish persistent Command & Control (C2) communication channels, and exfiltrate sensitive data.

In this lab, I deployed **pfSense Community Edition** as an enterprise virtual router and stateful packet-filtering firewall.

I isolated my Windows workstation behind pfSense on a dedicated private virtual network segment, forwarded raw firewall state logs in real time via **Syslog (UDP 1514)** to my centralized **Splunk SIEM**, and investigated three core network attack scenarios:
1. **Inbound External Reconnaissance:** 
	- Capturing and analyzing TCP flags (`[S]`, `[R]`, `[F]`) generated during an external port scan against the WAN interface.
2. **Egress Policy Hardening:** 
	- Designing strict outbound rules to detect and drop unauthorized egress attempts (simulating raw TCP reverse shells or exfiltration on non-standard ports like `4444`).
3. **Automated C2 Beaconing Detection:** 
	- Using advanced SPL time-delta analytics (`streamstats`) to identify automated malware heartbeat patterns based on mathematically consistent communication intervals.

## Technical Hurdles & Troubleshooting

### 1. Unprivileged Syslog Ingestion on Linux (Port 514 vs 1514)
* **The Problem:** 
	* In standard Linux operating systems, ports below 1024 are privileged. ç
	* Because Splunk Enterprise runs under a dedicated, unprivileged service account (`splunk`), binding directly to default Syslog port `UDP 514` resulted in an OS permission denied error.
* **The Fix:** 
	* Rather than running Splunk insecurely as `root`, I configured Splunk to listen on high-port **UDP 1514** and mapped pfSense's remote logging destination explicitly to `192.168.10.128:1514`.

### 2. Firewall Rule Ordering (First-Match Wins)
* **The Problem:** 
	* When creating the custom egress block rule for port `4444`, test outbound connections failed, but pfSense logged zero events - neither in the local Web UI nor in Splunk.
* **The Root Cause:** 
	* pfSense evaluates firewall rules from **top to bottom**, terminating evaluation on the first matching rule ("first-match wins"). 
	* By default, pfSense places a permissive `Default allow LAN to any rule` at the top of the LAN list. 
	* Because my block rule was created below the allow rule, outbound packets matched the allow rule first and bypassed the block inspection entirely.
* **The Fix:** 
	* I moved the egress block rule to the very top of the LAN table (above the default allow rule) .

### 3. Source Scope: `LAN Address` vs. `LAN Subnet`
* **The Problem:** 
	* Even with the rule placed at the top, outbound packets from the Windows VM were still passing through without triggering the drop rule.
* **The Root Cause:** 
	* In pfSense, selecting `LAN Address` as the rule's source scope restricts the rule strictly to traffic originating from the firewall's *own* local interface IP (`192.168.1.1`). 
	* It did not apply to traffic generated by client machines inside the subnet.
* **The Fix:** 
	* I changed the rule source from `LAN Address` to **`LAN Net`** (or `LAN Subnet`), encompassing all hosts within the `192.168.1.0/24` CIDR block. 
	* Immediately, retransmitted SYN connection packets from `192.168.1.100` matched the rule and logged red drop events.

## Investigation Scenarios & Telemetry Analysis

### Parsing Raw pfSense `filterlog` in Splunk

pfSense outputs firewall state events as comma-separated values (CSV) under the system identifier `filterlog`. 

Rather than relying on custom third-party parser add-ons, I dynamically extracted fields using Splunk’s built-in `makemv` and `mvindex` functions:

* **Index 5:** Action (`block` vs. `pass`)
* **Index 6:** Direction (`in` vs. `out`)
* **Index 14:** Protocol (`tcp`, `udp`, `icmp`)
* **Index 16:** Source IP address
* **Index 17:** Destination IP address
* **Index 19:** Destination port
* **Index 21:** TCP Control Flags (`S`, `A`, `R`, `F`)

## Key Lessons Learned

1. **Firewall Rule Processing Mechanics:** 
	- Stateful firewalls process rules sequentially from the top down. 
	- Misplacing a restrictive drop rule below a general allow rule renders the protection completely ineffective.
2. **Interface Scope Matters:** 
	- Setting a rule source to `LAN Address` protects only the router itself, whereas `LAN Subnet` enforces policy across all client workstations behind that gateway.
3. **Multi-Source Correlation (Perimeter + Endpoint):** 
	- A firewall log provides the connection metadata (source IP, destination IP, port, and TCP flags), but it cannot tell you *what application* made the request. 
	- Cross-referencing firewall drop timestamps with endpoint EDR telemetry (Sysmon Event 3 or LimaCharlie network sockets) bridges the gap between network and host security.
4. **Behavioral Detection via Time-Delta Math:** 
	- Traditional firewalls filter on static IPs and ports. 
	- Modern threat hunting identifies malicious intent through behavior - measuring communication intervals (`streamstats`) uncovers stealthy beacons even when communicating over legitimate, allowed ports (HTTP/HTTPS).
